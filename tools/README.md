# tools/

Standalone scripts that sit outside the `packages/*`/`apps/*` workspaces — CLIs and
browser-automation helpers, run directly with `node` (or `python3` for the one exception), no
build step of their own. Each file's own header comment is the source of truth; this is an index.

| Tool | What it's for |
|------|----------------|
| [`zpcr.mjs`](./zpcr.mjs) | `node tools/zpcr.mjs <run> results\|curves [--password <pw>] [--step <n>]`, or `node tools/zpcr.mjs <out.zpcr> new --name <name> --protocol <p.prcl.txt> [--plate <p.plt.csv>] [--force]` — `<run>` is any of the three run formats (CFX `.zpcr`/`.pcrd`, Biomeme `.bmrun`), routed on extension the way the app routes a dropped file. `results` prints a run's results table (the web app's Curves view Table mode / CSV download) as CSV on stdout; `curves` writes a PNG of the amplification curves as the Curves chart draws them in Relative mode — same colors, same dark background, a ring at each Cq — with `--wells`/`--rows`/`--cols`/`--fluors` to pick what's plotted and `--size`/`--dpr` to size it (`--size` is CSS pixels, `--dpr` multiplies them into device pixels as a retina display would, so `--size 640x360 --dpr 2` is a 1280×720 file of the 640-wide chart rather than the smaller-lettered chart `--size 1280x720` lays out). `new` goes the other way and *writes* a file: a pending experiment — a `.zpcr` carrying a protocol, the run's name and optionally a plate, with no plate reads and no `begun` marker — the same thing the app's "New experiment" creates, ready to open there and start on an instrument. A thin CLI over `@zpcrweb/core`'s `computeRunAnalysis`/`buildAnalysisRows`/`analysisCsv` (and `buildExperimentArchive` for `new`), so it's the same numbers the UI shows for the same file — and `curves` is drawn by the app's own chart module in headless Chrome ([`chartshot.mjs`](./chartshot.mjs)), so it's the same picture too. Needs a built core (`npm run build`); `curves` also needs Chrome. |
| [`cfx.mjs`](./cfx.mjs) | `node tools/cfx.mjs info\|status\|ls\|get [--trace]` — talks to a live CFX96/C1000 instrument over USB from the command line: identification, status, directory listing, file download, and (`--trace`) a raw framed-message log. Every subcommand is a named `CfxDevice` operation — no "send this command line" escape hatch. The Node face of the same `@zpcrweb/core` USB client the web app's Instrument view drives in the browser — see [`usb.md`](../usb.md). Needs the optional `usb` dependency and a built core. |
| [`uishot.mjs`](./uishot.mjs) | `node tools/uishot.mjs [--views ...] [--file ...] [--max-width ...]` — one-call headless-Chrome screenshot check: boots its own dev server and Chrome on random ports, loads a sample file, walks the requested views, and writes a single labelled contact-sheet PNG plus a text report of console/page errors. See `AGENTS.md`'s "UI testing" for when to reach for it and how to keep it cheap. |
| [`uitest.mjs`](./uitest.mjs) (`npm run test:ui`) | Headless-Chrome browser assertions for what the core Vitest suite (no DOM) and a screenshot (no interaction) can't catch: URL hash routing, password handling, the rail chips' interaction contract, the Curves table's sort/filter behavior, the protocol editor's click-to-edit/insert/delete/undo contract, the `.alf` run report's derived columns, the disk-backed folder route (whose directory picker can't be driven from CDP, so an origin-private directory stands in for it), and more. ~100s, needs Chrome, deliberately not part of `npm test`. See `AGENTS.md`'s "UI testing" for which source files should make you run it. |
| [`harness.mjs`](./harness.mjs) | Shared library for `uishot.mjs` and `uitest.mjs` — the CDP client (talks the Chrome DevTools Protocol directly over Node's `WebSocket`, no Puppeteer) and dev-server/Chrome process plumbing, the waiting vocabulary a check should be written in (`waitFor` for a condition, `waitValue` for a value that is about to change, `waitStable` for one the app writes more than once, `flushWrites` to hide the page and make the app's rate-limited writes land now rather than on their own timer), plus `buildCore()`, which refreshes `@zpcrweb/core`'s `dist/` so a script that imports the library from Node doesn't test the page's current source against a months-old build. Not a script itself; add new browser-automation checks here rather than starting a third tool. |
| [`chartshot.mjs`](./chartshot.mjs) | Shared library for `zpcr.mjs curves` — renders the web app's Curves chart to a PNG from Node by running the real thing: esbuild bundles `apps/web`'s `buildChart` plus uPlot into one self-contained HTML page, headless Chrome opens it from a `file://` URL with the caller's curves injected as JSON, and the page comes back as a PNG. The bundle is rebuilt on every run, so the picture cannot go stale against the chart it came from. Not a script itself; needs Chrome. |
| [`usbpcap_decode.py`](./usbpcap_decode.py) | `python3 tools/usbpcap_decode.py <file.pcapng> [--device N] [--raw]` — decodes a USBPcap capture of CFX96 traffic: per-device VID:PID and packet counts with no args, or the full decoded command/response stream for one device. Standalone analysis tool used to validate `usb.md` against real captures, not part of the built app. Requires `pip install dpkt`. |

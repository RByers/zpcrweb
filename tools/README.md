# tools/

Standalone scripts that sit outside the `packages/*`/`apps/*` workspaces — CLIs and
browser-automation helpers, run directly with `node` (or `python3` for the one exception), no
build step of their own. Each file's own header comment is the source of truth; this is an index.

| Tool | What it's for |
|------|----------------|
| [`zpcr.mjs`](./zpcr.mjs) | `node tools/zpcr.mjs <file.zpcr> results\|curves [--password <pw>] [--step <n>]` — `results` prints a run's results table (the web app's Curves view Table mode / CSV download) as CSV on stdout; `curves` writes a PNG of the amplification curves as the Curves chart draws them in Relative mode — same colors, same dark background, a ring at each Cq — with `--wells`/`--rows`/`--cols`/`--fluors` to pick what's plotted. A thin CLI over `@zpcrweb/core`'s `computeRunAnalysis`/`buildAnalysisRows`/`analysisCsv` (and its `colors.ts` palette) — no app code involved, so it's the same numbers and the same hues the UI shows for the same file. Needs a built core (`npm run build`). |
| [`cfx.mjs`](./cfx.mjs) | `node tools/cfx.mjs info\|status\|ls\|get [--trace]` — talks to a live CFX96/C1000 instrument over USB from the command line: identification, status, directory listing, file download, and (`--trace`) a raw framed-message log. Every subcommand is a named `CfxDevice` operation — no "send this command line" escape hatch. The Node face of the same `@zpcrweb/core` USB client the web app's Instrument view drives in the browser — see [`usb.md`](../usb.md). Needs the optional `usb` dependency and a built core. |
| [`uishot.mjs`](./uishot.mjs) | `node tools/uishot.mjs [--views ...] [--file ...] [--max-width ...]` — one-call headless-Chrome screenshot check: boots its own dev server and Chrome on random ports, loads a sample file, walks the requested views, and writes a single labelled contact-sheet PNG plus a text report of console/page errors. See `AGENTS.md`'s "UI testing" for when to reach for it and how to keep it cheap. |
| [`uitest.mjs`](./uitest.mjs) (`npm run test:ui`) | Headless-Chrome browser assertions for what the core Vitest suite (no DOM) and a screenshot (no interaction) can't catch: URL hash routing, password handling, the rail chips' interaction contract, the Curves table's sort/filter behavior, the protocol editor's click-to-edit/insert/delete/undo contract, the `.alf` run report's derived columns, and more. ~100s, needs Chrome, deliberately not part of `npm test`. See `AGENTS.md`'s "UI testing" for which source files should make you run it. |
| [`harness.mjs`](./harness.mjs) | Shared library for `uishot.mjs` and `uitest.mjs` — the CDP client (talks the Chrome DevTools Protocol directly over Node's `WebSocket`, no Puppeteer) and dev-server/Chrome process plumbing, plus `buildCore()`, which refreshes `@zpcrweb/core`'s `dist/` so a script that imports the library from Node doesn't test the page's current source against a months-old build. Not a script itself; add new browser-automation checks here rather than starting a third tool. |
| [`png.mjs`](./png.mjs) | Shared library for `zpcr.mjs curves` — a software rasterizer (anti-aliased lines, dashes, circles, 5×7 bitmap text) and a PNG encoder built on `node:zlib`. Exists so a chart can be drawn on a machine with Node and nothing else: no browser, no native image module, no `npm install`. Not a script itself, and deliberately minimal — anything needing fills, gradients or real glyph shaping should be rendered in a browser instead. |
| [`usbpcap_decode.py`](./usbpcap_decode.py) | `python3 tools/usbpcap_decode.py <file.pcapng> [--device N] [--raw]` — decodes a USBPcap capture of CFX96 traffic: per-device VID:PID and packet counts with no args, or the full decoded command/response stream for one device. Standalone analysis tool used to validate `usb.md` against real captures, not part of the built app. Requires `pip install dpkt`. |
